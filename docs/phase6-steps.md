# Artoria Phase 6 手順書: 差分とALTER(B-2)

ゴール: 既存DBのスキーマを編集し、**変更分だけ**を安全にDBへ反映できるようにする。

**前提**: Phase 5 完了(既存DBを `Schema` として読み取れ、`baseline`(元)付きで保存できる)。

## Step 0: 設計判断: 名前変更をどう検出するか

**問題**: 「元」と「現在」を比べるだけだと、次の2つの区別が付かない。

- カラム `Name` を削除して、`FullName` を追加した
- カラム `Name` の名前を `FullName` に変更した

前者は **データが消える**。後者は `sp_rename` でデータが残る。意味が全く違う。

**選択肢**

| 方式 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **A: ID方式(おすすめ)** | `Table` と `Column` に、変わらない `id`(UUIDなど)を持たせる。名前が変わっても、同じIDなら「同じもの」 | 差分計算が単純で正確 | モデル・ファイル形式の変更が必要 |
| B: 操作ログ方式 | 画面での編集操作(名前変更など)を、すべてログとして残す | モデルを変えなくてよい | ログと実際の状態のずれを防ぐ必要がある。Undoとの整合が複雑 |
| C: 推測方式 | 型・位置が同じなら名前変更とみなす | 実装が簡単 | 誤判定でデータが消えうる。**危険** |

**説明**
- **Cは選ばない。** 誤判定が、そのままデータ消失になる
- Aなら、Phase 5の `build_schema` が読み取り時にIDを付与し、`baseline` と `schema` の両方に同じIDが入る。画面での名前変更は、IDを保ったまま名前だけを変える。新規追加したものには新しいIDを付ける
- IDの付与は、`format_version` を上げて、古いファイルは読み込み時に付与する(Phase 3で作った変換の置き場所を使う)
- Phase 2の編集操作(Step 1)は「名前変更」を専用の操作として作ってあるので、IDを保つ形に修正しやすい

**確認**: 方式を決めて、`roadmap.md` または別メモに記録する。Aを選ぶなら、モデルへの `id` 追加、`format_version` 上げ、Phase 1〜5のテストの修正まで終える。

## Step 1: 差分のデータ構造

**やること**: `artoria-core/src/diff.rs` を作り、差分を表す型を定義する。

```text
SchemaDiff { tables: Vec<TableChange> }

TableChange
  ├─ Added(Table)
  ├─ Removed(Table)
  ├─ Renamed { id, from, to }            // スキーマ名の変更も含む
  └─ Modified { id, columns, primary_key, foreign_keys, indexes }

ColumnChange
  ├─ Added(Column)
  ├─ Removed(Column)
  ├─ Renamed { id, from, to }
  └─ Modified { id, from: Column, to: Column }   // 型・NULL可否・IDENTITY・DEFAULT の変更

PrimaryKeyChange / ForeignKeyChange / IndexChange も同様に Added / Removed / Modified
```

**説明**
- 「Modified」は、変更前と変更後の両方を持つ。ALTER文の生成と、危険判定(型が縮小したか、など)の両方で必要になる
- **主キー・外部キー・インデックスの「変更」は、「削除して再作成」として扱う**。SQL Serverにはこれらを直接変更する `ALTER` がほぼないため。差分の型としては `Modified` を持たせ、SQL化(Step 3)で「DROP → CREATE」に展開する
- すべてに `Debug` / `Clone` / `PartialEq` を付ける(テストで比較する)

**確認**: コンパイルが通り、手で作った `SchemaDiff` を `==` で比較できる。

## Step 2: 差分の計算

**やること**: 次の関数を書く。

```text
diff_schemas(baseline: &Schema, current: &Schema) -> SchemaDiff
```

**処理の流れ(Step 0でA方式を選んだ場合)**

1. テーブルをIDで突き合わせる
   - `baseline` にだけある → `Removed`
   - `current` にだけある → `Added`
   - 両方にある → 中身を比較する(名前が違えば `Renamed`、それ以外の違いは `Modified`)
2. 両方にあるテーブルについて、カラムをIDで突き合わせる(同様に Added / Removed / Renamed / Modified)
3. 主キー・外部キー・インデックスは、名前または内容で突き合わせる
4. **変更がなければ、空の `SchemaDiff` を返す**

**説明**
- 比較は、Phase 1で付けた `PartialEq` を使う。細かい違い(型だけ違う、NULL可否だけ違う)を区別して `Modified` に入れる
- **カラムの並び順の変更**は、SQL Serverでは `ALTER` で直接できない(テーブルの作り直しが必要)。**差分としては無視する**(または警告に出す)。多くの用途で、並び順の変更は実害がない
- 差分計算は純粋な関数なので、**テストを厚く書ける**。ここが一番テストの価値が高い

**確認(テストで)**: 次のケースを個別にテストする。
- 変更なし → 空
- テーブル追加 / 削除 / 名前変更
- カラム追加 / 削除 / 名前変更 / 型変更 / NULL可否変更 / DEFAULT変更
- 主キーの変更、FKの追加、インデックスの削除
- 複数の変更が混在する
- **カラム `A` を削除して `B` を追加**(IDが違う)と、**`A` を `B` に名前変更**(IDが同じ)が、別の結果になる

## Step 3: 差分から `ALTER` 文の生成

**やること**: 次の関数を書く。

```text
generate_migration(&SchemaDiff, baseline: &Schema, current: &Schema) -> Vec<MigrationStep>
```

`MigrationStep` は、SQL文と、その意味(説明文、危険度)を持つ構造体。Phase 4で作った文のリスト実行に渡せる形にする。

**変更ごとのSQL**

| 変更 | SQL |
|---|---|
| テーブル追加 | `CREATE TABLE`(Phase 1の関数を再利用) |
| テーブル削除 | `DROP TABLE [スキーマ].[テーブル]` |
| テーブル名変更 | `EXEC sp_rename 'スキーマ.旧名', '新名'`(**新名には、スキーマを付けない**) |
| カラム追加 | `ALTER TABLE ... ADD [名前] 型 NULL/NOT NULL ...` |
| カラム削除 | `ALTER TABLE ... DROP COLUMN [名前]` |
| カラム名変更 | `EXEC sp_rename 'スキーマ.テーブル.旧名', '新名', 'COLUMN'` |
| カラム変更(型・NULL可否) | `ALTER TABLE ... ALTER COLUMN [名前] 型 NULL/NOT NULL` |
| PK / FK / インデックスの追加 | Phase 1の関数を再利用 |
| PK / FK / インデックスの削除 | `ALTER TABLE ... DROP CONSTRAINT [名前]` / `DROP INDEX [名前] ON ...` |

**実行順序(重要)**

依存関係があるため、次の順序で並べる。

1. 外部キーの削除
2. インデックスの削除
3. 主キーの削除
4. テーブルの削除
5. テーブル・カラムの名前変更
6. カラムの追加 / 型変更 / 削除
7. テーブルの追加
8. 主キーの追加
9. インデックスの追加
10. 外部キーの追加

**説明**
- 外部キーを先に消しておけば、**テーブルやカラムを自由に変更できる**。最後にまとめて作り直す。Phase 1の「FKを後から付ける」と同じ考え方
- `ALTER COLUMN` は、**NULL可否を省略すると NULL許可に戻る**。変更しない項目でも、現在の値を毎回明示する
- カラム追加で `NOT NULL` かつ既存の行がある場合、DEFAULTがないと失敗する。Step 5の警告対象にする
- `sp_rename` は、実行すると警告メッセージが出る(「名前を変更すると、スクリプトやストアドプロシージャが壊れる可能性があります」)。これは正常な動作

**確認(テストで)**: 各変更ごとに、期待するSQLの文字列と並び順をテストする。Phase 1と同じ流れ(期待値を先に書く)。

## Step 4: 難所: 依存オブジェクトを伴う変更

**ここが、最も複雑で、事故の多い部分。** 一度に全部を作ろうとせず、1つずつ対応する。

### 4-1: DEFAULT制約

- SQL Serverでは、DEFAULTは **名前付きの制約**(`DF_...`)としてできる。名前を付けずに作っても、システムが自動で名前を付ける(`DF__Users__Created__3B75D760` のような名前)
- DEFAULTを変更・削除するには、**制約名を指定して `DROP CONSTRAINT` する必要がある**
- 対応: Phase 5で読み取るとき、DEFAULT制約の名前もモデルに持つ(`default_name: Option<String>`)。Phase 1のDDL生成でも、`CONSTRAINT [DF_テーブル_カラム] DEFAULT ...` と名前付きで作るよう改める

### 4-2: カラムの型変更ができない場合

次のものがカラムに依存していると、`ALTER COLUMN` は失敗する。

- インデックス
- 主キー・外部キー
- DEFAULT制約
- CHECK制約

対応: **依存するものを先に `DROP` し、変更後に再作成する**。Step 3の実行順序(FK・インデックス・PKを先に消す)で、ほとんどのケースは解決する。DEFAULT制約は、4-1の対応で個別に処理する。

### 4-3: 型変更の互換性

- 変換できない型の組み合わせがある(`UNIQUEIDENTIFIER` → `INT` など)
- 変換できても、データが失われる(長さの縮小、`DECIMAL` の小数桁の縮小)
- 対応: Step 5の危険判定で、**変換可能か・安全かを分類**して警告する。変換不可の組み合わせは、実行前にエラーにする

### 4-4: IDENTITYの変更

- 既存のカラムに `IDENTITY` を後から付ける、または外す操作は、**`ALTER COLUMN` ではできない**
- 対応: 「テーブルの作り直し(新テーブル作成 → データ移行 → 旧テーブル削除 → 名前変更)」が必要になる。**最初は未対応として、実行前にエラーで止める**(「IDENTITYの変更は未対応です」)。ユーザーが誤って壊すより、できないと伝える

**判断メモ**: 対応できない変更は、**黙って無視せず必ず警告・エラー**にする。サポート範囲を狭く保つほうが安全。

**確認**: 4-1〜4-4それぞれについて、テストを書く。特に、DEFAULT付きのカラムの型変更が、DB上で成功する(Step 6で確認)。

## Step 5: 危険な変更の判定

**やること**: `MigrationStep` ごとに、危険度を付ける。

| 危険度 | 例 |
|---|---|
| **破壊的(データが消える)** | テーブル削除、カラム削除、長さ・精度の縮小、型変換でデータが切り捨てられうる変更 |
| **失敗しうる** | NULL許可 → NOT NULL(既存行にNULLがあると失敗)、NOT NULLのカラム追加でDEFAULTなし、UNIQUEインデックス・UNIQUE制約の追加(重複があると失敗)、FKの追加(参照先にない値があると失敗) |
| **注意** | 名前変更(参照しているビュー・プロシージャが壊れる)、大きなテーブルでのカラム型変更(時間がかかる・ロックされる) |
| 安全 | ほとんどの追加操作 |

**説明**
- 危険度は、**警告の文言を付けて、画面に表示する**。「このカラムを削除すると、データが完全に失われます」のように具体的に
- 「失敗しうる」ものは、可能なら **実行前にDBに問い合わせて確かめる**
  - NULL許可 → NOT NULL: `SELECT COUNT(*) FROM ... WHERE [列] IS NULL`
  - UNIQUEの追加: `GROUP BY ... HAVING COUNT(*) > 1`
  - FKの追加: `LEFT JOIN ... WHERE 参照先 IS NULL`
- 「破壊的」な変更は、**行数を確認して表示する**(「削除するテーブルには、1,234,567行のデータがあります」)。件数の取得は、`sys.dm_db_partition_stats` で概算できる(正確な `COUNT(*)` は大きなテーブルで重い)

**確認(テストで)**: 各変更が期待どおりの危険度に分類される。

## Step 6: DB上での往復テスト

**やること**: Dockerの練習用DBを使って、実際に動くことを確認する自動テストを書く。

```text
1. スキーマAを作成(generate_ddl + execute)
2. DBを読み込む(read_schema) → baseline
3. baseline をコピーして編集 → current(スキーマB)
4. diff → generate_migration → execute
5. DBを再び読み込む(read_schema)
6. 読んだ結果 == current ?
```

**説明**
- Phase 5の往復テストの発展形。**差分適用の正しさを、DBそのものを使って確認できる**
- テストするパターン(1つずつ別のテストにする)
  - カラム追加・削除・名前変更
  - 型変更(DEFAULT付き・インデックス付きのカラムを含む)
  - NULL可否の変更
  - FKの追加・削除
  - インデックスの追加・削除
  - テーブルの追加・削除・名前変更
  - すべてを同時に行う
- **データが入った状態でのテスト**も入れる(名前変更でデータが残る、型変更でデータが保たれる、など)
- 各テストの前後で、テスト用DBをきれいに戻す(全テーブルを `DROP` する補助関数を用意する)

**確認**: すべてのパターンで、往復が成り立つ。

## Step 7: 差分プレビュー画面

**やること**
- 「変更をデータベースに反映」ボタンで、差分プレビューの画面を開く
- 表示内容:
  - 変更の一覧(追加 / 変更 / 削除を色分け。`+` `~` `-` の記号も併用する)
  - 各変更の、変更前→変更後
  - 生成されるSQLの全文
  - 危険度の警告(Step 5)。**破壊的なものは赤で目立たせる**
- ツリー表示(テーブル → カラム)で、変更のある場所だけを展開して見せる

**説明**
- 差分が空のときは、「変更はありません」と表示して、実行を無効にする
- **変更の1つ1つを、ユーザーが選んで取り消せる**機能は、後回しにする(依存関係の整合が複雑になるため)。最初は「全部適用」か「やめる」だけ
- 色だけに頼らない(色覚の違いがあるため)。記号と文字でも区別できるようにする

**確認**: 複数の変更を含む編集をして、差分プレビューに期待どおりの一覧とSQLが出る。

## Step 8: ドリフト検出

**ドリフトとは**: 設計(`baseline`)を読み込んでから実行するまでの間に、**他の人がDBを変更していた**状態。

**やること**
- 「実行」の直前に、DBをもう一度読み込み、`baseline` と比較する
- 違いがあれば、**実行を中止して**、何が変わっていたかを表示する
- ユーザーは、(1)DBを再読み込みして編集をやり直す、(2)取りやめる、のどちらかを選ぶ

**説明**
- ドリフトを無視して `ALTER` を流すと、**他の人の変更を壊す**、または想定外の状態になる
- 比較は `read_schema` の結果と `baseline` の `==` で行う。**Phase 5の往復テストでDEFAULTの表記ゆれなどを解決しておく**と、ここで誤検出が起きない
- 読み取れない情報(Phase 5で警告として捨てたもの)に変更があっても、検出できない。これは仕様として、READMEに書いておく
- 実行直前の再読み込みと、実際の実行の間にも、わずかな隙間がある。完全には防げないが、**`BEGIN TRANSACTION` の中で再読み込みする**ことで、隙間を狭められる(SQL Serverの分離レベルによる)

**確認(テストで)**: 読み込み後、別の接続でDBを変更し、実行すると中止される。変更がなければ通常どおり実行できる。

## Step 9: 実行

**やること**
- Phase 4の実行基盤(トランザクション、確認ダイアログ、ログ、環境ラベル)を再利用する
- 実行前の確認ダイアログに、**破壊的な変更の件数と内容**を、目立つ形で追加する
- 破壊的な変更を含むときは、追加の確認(「削除する」と入力させる、チェックボックスにチェックさせる、など)
- 実行後、**DBを再読み込みして、`baseline` と `current` を両方とも更新する**(「元」を最新の状態にする)
- 実行ログに、差分の内容(何をどう変えたか)も残す

**説明**
- 実行後に再読み込みしないと、次の編集で「すでに適用済みの変更」がもう一度差分に出てしまう
- 実行が失敗したときは、`ROLLBACK` され、`baseline` はそのまま。画面も編集中の状態のまま残し、やり直せる

**確認**: 練習用DBで、複数の変更を一度に適用し、成功すれば差分がなくなる。失敗すれば何も変わらず、編集内容が残る。

## つまずきやすい点

- **`sp_rename` の引数**: 新しい名前には、スキーマ名もテーブル名も付けない(名前だけ)。付けると、`dbo.dbo.NewName` のような名前になる
- **`ALTER COLUMN` でNULL可否が戻る**: 変更しない項目も、毎回明示する(Step 3)
- **DEFAULT制約の名前が分からない**: Step 4-1のとおり、読み取り時に名前を取り、作成時にも名前を付ける
- **差分が出続ける**: DBが返す値の表記と、`Schema` の表記が食い違っている(Phase 5のDEFAULTの正規化など)。**変更していないのに差分が出る**ときは、まずここを疑う
- **テストの後始末**: テストが失敗したままDBに残骸が残ると、次のテストが連鎖して失敗する。テストの前に必ずDBをきれいにする
