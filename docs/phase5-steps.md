# Artoria Phase 5 手順書: 既存DBの読み取り(B-1)

ゴール: 既存のSQL Serverの構造を、Phase 1と同じ `Schema` として読み取り、画面で閲覧できるようにする。

**前提**: Phase 4 完了(接続・実行ができる。練習用のDockerのSQL Serverがある)。

**この設計の肝**: DBを読んだ結果を、**Phase 1と同じ `Schema` 型に変換する**。そうすれば、Phase 2の画面・Phase 3の保存・Phase 1のDDL生成が、そのまま使える。

## Step 0: モデルの拡張を決める

**なぜ必要か**: Phase 1のモデルは「ゼロから作る」ことを前提にしていた。既存DBには、モデルが表現できない情報がある。読み取って、再びDDLにするときに、**情報が落ちると差分が誤判定される**。

**確認する項目(それぞれ、追加するか、警告して捨てるかを決める)**

| 項目 | 問題 | おすすめ |
|---|---|---|
| **主キーの制約名** | Phase 1は `PK_テーブル名` で自動命名。既存DBの名前が違うと、Phase 6の差分で「違う」と判定される | `primary_key_name: Option<String>` を `Table` に追加(`None` なら自動命名) |
| **外部キーのON DELETE / ON UPDATE** | 既存DBでCASCADEが使われている場合が多い | `FkAction`(NoAction / Cascade / SetNull / SetDefault)を追加 |
| **クラスター化インデックス** | PKは既定でクラスター化されるが、そうでないDBもある | まず警告して捨てる。必要になったら追加 |
| **インクルード列・フィルター付きインデックス** | モデルにない | 警告して捨てる |
| **計算列・スパース列・照合順序の指定** | モデルにない | 警告して捨てる |
| **CHECK制約、UNIQUE制約、トリガー、ビュー** | モデルにない | 警告して捨てる(Phase 7の候補) |
| **IDENTITYの開始値・増分** | 今は `(1,1)` 固定 | 開始値・増分が `1,1` 以外なら警告 |

**説明**
- **「捨てる」場合は、必ず警告に出す。** 黙って落とすと、Phase 6で「変更を適用した」ときにその設定が失われる
- モデルを拡張するときは、Phase 3で作った `format_version` を上げる。新しいフィールドには `#[serde(default)]` を付けて、古いファイルも読めるようにする
- Phase 1・2のテストと画面の修正が必要になる。**最小限の拡張(主キー名とFKアクションの2つ)から始める**

**確認**: モデルを拡張し、Phase 1〜3のテストがすべて通る。古い形式のファイル(拡張前に保存したもの)が読める。

## Step 1: カタログビューを読むクエリと、中間データ構造

**やること**: `artoria-db/src/catalog.rs` を作る。SQL Serverの **システムカタログビュー** から情報を読むクエリを書き、結果を中間の構造体(行の構造体)に入れる。

**読むカタログビュー**

| 目的 | ビュー |
|---|---|
| スキーマ一覧 | `sys.schemas` |
| テーブル一覧 | `sys.tables`(`schema_id` でスキーマと結合) |
| カラム | `sys.columns`(`object_id` でテーブルと結合)、`sys.types`(型名) |
| IDENTITY | `sys.identity_columns`(または `sys.columns.is_identity`) |
| DEFAULT | `sys.default_constraints` |
| 主キー・UNIQUE制約 | `sys.key_constraints`、`sys.indexes`、`sys.index_columns` |
| インデックス | `sys.indexes`、`sys.index_columns`(`key_ordinal` でカラム順) |
| 外部キー | `sys.foreign_keys`、`sys.foreign_key_columns` |

**説明**
- 読むクエリは、**目的ごとに分ける**(テーブル、カラム、PK、FK、インデックスで1つずつ)。1つの巨大なJOINにしない。結果の行の構造体も、クエリごとに1つ作る
- 例: `ColumnRow { schema, table, column, column_id, type_name, max_length, precision, scale, is_nullable, is_identity, default_definition }`
- **ユーザー定義のオブジェクトだけ**を読む。`sys.tables` の `is_ms_shipped = 0` で絞る。システムのテーブルを読まないようにする
- 複合キー(複数カラムのPK・FK・インデックス)は、`key_ordinal` や `constraint_column_id` の順に並べて取る。**順序が重要**
- `sys.*` の列名は、バージョンで増えることがある。必要な列だけを `SELECT` に書く
- `tiberius` で行を読むには、`Row::get::<型, _>("列名")` を使う。NULLがありうる列は `Option<型>` で取る(型が合わないと、実行時にエラーになる)

**確認(Dockerの練習用DBで)**: Phase 4で作ったスキーマの内容が、各クエリの結果に現れる。`ColumnRow` の件数がカラム数と一致する。

## Step 2: 行から `Schema` への変換(DBなしでテストできる部分)

**やること**: 次の形の関数を書く。

```text
build_schema(rows: CatalogRows) -> (Schema, Vec<ReadWarning>)
```

`CatalogRows` は、Step 1の各行の構造体のリストをまとめたもの。

**説明**
- この関数は **DBに依存しない純粋な関数** にする。入力は構造体のリスト、出力は `Schema`。`artoria-core` の中に置いてもよい。**テストが書きやすい**(DBなしで、手書きの行のリストから `Schema` を作って期待どおりか確認できる)
- 処理の流れ:
  1. テーブルを `(スキーマ, テーブル名)` ごとに作る
  2. カラムを `column_id` の順に並べて、そのテーブルに入れる
  3. 主キーのカラムを `key_ordinal` の順で `primary_key` に入れる
  4. 外部キーを、`constraint_column_id` の順でカラムのペアにする
  5. インデックスを入れる(PKに対応するインデックスは、インデックスの一覧から除く。そうしないと二重になる)
- **テーブルの並び順を決める**(スキーマ名、テーブル名の順にソートする)。DBが返す順序は保証されないため。そうしないと、同じDBを2回読んだ結果が `==` にならないことがある

**確認(テストで)**: 手書きの行(`Users`、`Orders` とFKとインデックス)から、Phase 1の `sample_schema()` と `==` になる `Schema` が作れる。

## Step 3: 型のマッピングと「読み取れないもの」の警告

**やること**: カタログの型名を `SqlType` に変換する関数と、警告の型を作る。

```text
map_type(type_name, max_length, precision, scale) -> Result<SqlType, Unsupported>
```

**型の対応**

| `sys.types` の名前 | `SqlType` | 備考 |
|---|---|---|
| `int` | Int | |
| `bigint` | BigInt | |
| `bit` | Bit | |
| `datetime2` | DateTime2 | 精度(`datetime2(3)` など)は今のモデルにない。既定の7以外は警告 |
| `uniqueidentifier` | UniqueIdentifier | |
| `decimal` / `numeric` | Decimal(precision, scale) | |
| `nvarchar` | NVarChar(長さ) | **`max_length` はバイト数。文字数は半分にする。`-1` はMAX(`None`)** |
| 上記以外(`varchar`、`datetime`、`money`、`xml` など) | 読み取れない | 警告 |

**説明**
- 読み取れない型のカラムがあるテーブルをどう扱うか、方針を決める
  - **方針A(おすすめ)**: カラムを読み取り結果から**外さず**、警告に「この型は未対応のため読み取れません」と出す。そのテーブルは**編集不可(読み取り専用)** にする
  - 方針B: 未対応の型を `SqlType::Unsupported(String)` として持つ。表示はできるが、DDL生成は不可。Phase 6の差分で再生成する場合は、この方式のほうが情報を失わない
- **`ReadWarning`** は、どのテーブル・カラム・項目で何が落ちたかを持つ構造体にする。画面で一覧表示する
- `datetime2` の精度などは、型名と別の列(`scale`)に入っている。型によって読む列が違うので、表にまとめておく

**判断メモ**: 今のモデルに入っていない型(`varchar`、`date`、`float` など)が既存DBには大量にある。**現実のDBを読むと、警告だらけになる**ことを想定する。Phase 7で型を拡張する優先度が、ここで上がる。

**確認(テストで)**: 型のマッピング表の全パターン、`nvarchar(100)`(`max_length = 200`)が `NVarChar(Some(100))` になる、`nvarchar(max)`(`-1`)が `NVarChar(None)` になる、未対応の型が警告になる。

## Step 4: `read_schema` の統合と往復テスト

**やること**

```text
read_schema(&ConnectionSettings) -> Result<(Schema, Vec<ReadWarning>), DbError>
```

接続 → Step 1のクエリを全部実行 → Step 2の `build_schema` → 結果を返す。

**往復テスト(最重要)**

```text
sample_schema()
  → generate_ddl
  → execute_ddl(練習用DBに適用)
  → read_schema(同じDBを読む)
  → 読んだ Schema == 元の sample_schema() ?
```

**説明**
- この往復テストが通れば、**書く側(Phase 1〜4)と読む側(Phase 5)の整合が取れている**。両側のバグを一度に見つけられる強力なテスト
- 通らない場合、差分の原因は次のどれかになりやすい
  - テーブルやカラムの並び順
  - 主キーの制約名(Step 0で対応していない場合)
  - DEFAULTの定義(下記)
  - インデックスのカラム順
- **DEFAULTの定義の表記**: SQL Serverは、`GETDATE()` を `(getdate())`、`0` を `((0))` のようにカッコ付き・小文字で返す。そのまま `default` に入れると、元の `GETDATE()` と `==` にならない。対処は2つ
  - 外側のカッコを1組外す(`((0))` → `(0)` ではなく `0` まで、と決めて、ルールをテストに書く)
  - 比較のときだけ、空白・カッコ・大文字小文字を正規化する
  - **どちらにするかを決めて、ルールをコメントに残す**。後のPhase 6の差分にも影響する
- テストは `#[ignore]` を付け、Docker起動時だけ `cargo test -- --ignored` で実行する形にしてもよい

**確認**: 往復テストが通る。

## Step 5: 読み込み画面(接続 → DB選択 → 読み取り)

**やること**
- メニューに「データベースから読み込み」を追加する
- 接続設定を選ぶ(Phase 4の接続設定一覧)
- 接続後、DBの一覧(`sys.databases` を読む)から対象を選ぶ。接続設定でDB名が決まっているなら、省略する
- 「読み込み」ボタンで、`read_schema` を実行する(Phase 4のStep 5の橋渡しを使う)
- 読み込み中は進捗を表示する(テーブル数が多いと時間がかかる)

**説明**
- 読み込みは**読み取りだけ**で、DBを変更しない。ただし、ユーザーが不安にならないよう、画面にそのことを書いておく
- 読み込み専用のユーザーで接続すれば、さらに安全。**必要な権限**(`VIEW DEFINITION` など)がないと、一部のカタログビューが空で返ってくることがある。これは「権限がなくて読めない」のか「ない」のか区別が付かないので、**権限の不足に気づける警告**を出せるとよい
- 読み取ったスキーマを、現在のドキュメントに置き換えるのか、新しいドキュメントとして開くのかを決める。**新しいドキュメントとして開く**(今の編集内容を消さない)のが安全

**確認**: 練習用DBを読み込み、画面が表示される。

## Step 6: 結果の表示と警告の表示

**やること**
- 読み込み後、Phase 2の画面(テーブル一覧・カラム編集・DDLプレビュー)に表示する
- 「読み込み時の警告」の一覧パネルを追加する
  - 警告の種類(未対応の型、未対応のインデックスの種類、など)ごとに分けて表示
  - クリックで該当のテーブル・カラムに移動
- 警告のあるカラム・テーブルに、画面上で印を付ける

**説明**
- この時点で、**まだ編集はできても、DBへの反映はできない**(Phase 6で差分を作る)。そのことを、画面で明確にする。編集できるのに反映できないのは、ユーザーが混乱する元になる。**読み取り専用の表示モードにしておく**のも1つの方法
- DDLプレビューは、「このスキーマを新しく作るなら」のDDLになる。既存DBの構造を見るという用途では便利だが、**「実行」ボタンは無効にする**(既存のテーブルと衝突するため)

**確認**: 警告のあるDB(`varchar` カラムがあるなど)を読み込み、警告が一覧に出て、クリックで場所に移動できる。

## Step 7: 「元のスナップショット」付きで保存

**やること**
- 読み込んだDBのスキーマを、プロジェクトファイルとして保存できるようにする
- ファイルに、**「読み込み時点のスキーマ(元)」と「現在のスキーマ(編集後)」の両方**を持たせる
- `format_version` を上げる

```text
{
  "format_version": 2,
  "name": "...",
  "schema": { ...現在... },
  "baseline": { ...読み込み時点... }   // 新規設計のときは null
}
```

**説明**
- Phase 6の差分は、「元」と「現在」の比較で計算する。**元を保存しておかないと、ファイルを開き直したときに差分が分からなくなる**
- 新規に設計したプロジェクトでは `baseline` は `null`(Phase 3の形式のまま読める)
- 接続先の情報(どのDBから読んだか)を `ProjectFile` に入れるかは、Phase 4の方針(プロジェクトに接続情報を入れない)を保つ。**入れるなら、サーバー名やDB名など、機密でない表示用の情報だけ**にする

**確認**: 読み込み → 保存 → 開き直しで、`schema` と `baseline` の両方が復元される。Phase 3の古い形式のファイルが読める。

## つまずきやすい点

- **読み込みが遅い**: テーブルごとにクエリを投げず、**ビュー全体を1回で取る**(目的ごとに1クエリ)。ここまでのStep 1の方針で解決する
- **DEFAULT・CHECKの定義が、大文字小文字や括弧で食い違う**: Step 4のとおり、方針を決めてテストに残す
- **名前の大文字小文字**: DBの照合順序によって、`Users` と `users` が同じになる場合と別になる場合がある。**Phase 1のバリデーションの「大文字小文字を区別しない比較」と整合しているか**確認する
- **権限不足で空に見える**: Step 5のとおり、権限の不足を警告に出せるようにする
- **`Row::get` の型違い**: `smallint` は `i16`、`tinyint` は `u8`、`int` は `i32`、`bit` は `bool`。型を間違えると実行時エラーになる
