## Step 1: core: ファイル形式(`ProjectFile`)の定義

**やること**: `artoria-core/src/project.rs` を作る。

```text
{
  "format_version": 1,
  "name": "プロジェクト名",
  "schema": { ...Schemaそのまま... }
}
```

対応するRustの構造体を定義し、`Serialize` / `Deserialize` を付ける。

**説明**
- `Schema` の中にプロジェクト名を入れず、**外側の `ProjectFile` に持たせる**。Phase 1でレビューした「SQL Serverのスキーマと名前が紛らわしい」問題を避けるため
- **`format_version` は必須。** 将来フィールドを足したり形を変えたりしたとき、古いファイルを判別して変換できる
- 将来フィールドを足すときのため、新しい項目には `#[serde(default)]` を付ける習慣にする。古いファイルに項目がなくても、既定値で読める(C#の `System.Text.Json` で、プロパティが欠けていても既定値になるのと同じ)

**判断メモ**
- 拡張子は `.artoria` などの独自拡張子にする。中身はJSONのままでよい(テキストエディタで開け、gitで差分が見られる)
- JSONは **整形して(`to_string_pretty`)保存する**。gitの差分が読みやすくなる

**確認**: `ProjectFile` を作って、JSON文字列に変換し、読み戻して `==` になるテスト。

## Step 2: core: 読み書き関数と安全な保存

**やること**: 次の関数を書く。

```text
save_project(path, &ProjectFile) -> Result<(), ProjectError>
load_project(path) -> Result<ProjectFile, ProjectError>
```

**安全な保存の手順(重要)**

1. 同じフォルダに一時ファイル(`xxx.artoria.tmp`)として書き込む
2. 書き込みが成功したら、一時ファイルを本来の名前に **リネームして置き換える**

**説明**
- ファイルを直接上書きすると、書き込み中にアプリが落ちた場合に、**元のファイルまで壊れる**。一時ファイルを経由すれば、失敗しても元のファイルが残る
- `load_project` では `format_version` を確認する
  - 自分が知っているより**新しい**バージョン → 「新しいバージョンのArtoriaで作られたファイルです」というエラー
  - 古いバージョン → 変換して読む(今はバージョン1だけなので、将来のための分岐の置き場所だけ作っておく)
- `ProjectError` は `thiserror` で定義する(ファイルが読めない、JSONが不正、バージョンが新しい、など)。画面にそのまま表示できる文言にする

**確認(テストで)**
- 一時フォルダに保存 → 読み戻して `==` になる
- 壊れたJSONを読むとエラーになる
- `format_version` が大きすぎるファイルを読むとエラーになる
- 保存後に一時ファイルが残っていない

## Step 3: 未保存の変更(dirty)の判定

**やること**: `Document` に「最後に保存した時点の `Schema`」を持たせる。

```text
is_dirty = (現在の Schema != 最後に保存した Schema)
```

**説明**
- Phase 1で `PartialEq` を付けたので、**比較するだけで判定できる**。「変更フラグ」を手作業で管理すると、Undoで元に戻した場合などに不整合になる。比較方式なら、編集して元に戻せば「未保存なし」に戻る
- 保存 / 読み込み / 新規作成のたびに、「最後に保存した時点」を更新する

**確認(テストで)**: 編集すると dirty、保存すると not dirty、編集して Undo で戻すと not dirty。

## Step 4: app: 開く・保存・名前を付けて保存

**やること**
- メニュー(またはツールバー)に「新規」「開く」「保存」「名前を付けて保存」を付ける
- ショートカット: `Ctrl+N` / `Ctrl+O` / `Ctrl+S` / `Ctrl+Shift+S`
- 現在のファイルパスを `Document` に持たせる(未保存の新規なら `None`)
- ウィンドウのタイトルに、ファイル名と未保存の印(`*`)を出す

**説明**
- ファイル選択ダイアログは、GPUIが提供する機能(パスを選ばせるダイアログ)を使う。**関数名は使っているバージョンで確認する**。見つからない場合は、ダイアログ用クレート(`rfd` など)を使う方法もある
- ファイル選択は非同期で結果が返ってくる。結果を受け取ってから、`load_project` / `save_project` を呼ぶ
- 「保存」はパスが `None` なら「名前を付けて保存」と同じ動作にする
- 開いたとき、**Undo履歴は空にする**

**確認**: 保存 → アプリを閉じる → 開き直して「開く」で、同じ状態が復元される。

## Step 5: 未保存の確認ダイアログ

**やること**: 未保存の変更があるとき、次の操作の前に確認する。

- 新規作成
- 別のファイルを開く
- ウィンドウを閉じる / アプリを終了する

選択肢は「保存する」「保存しない」「キャンセル」の3つ。

**説明**
- 確認の処理は **1か所の関数にまとめる**(`confirm_discard_changes()` のような形)。3つの操作から呼ぶ
- 「保存する」を選んだ後、保存が失敗または取り消された場合は、**元の操作(閉じるなど)を中止する**。ここを間違えると、データが消える
- ウィンドウを閉じる操作の横取りは、GPUIのウィンドウ終了前のフックで行う。**関数名は使っているバージョンで確認する**

**確認**: 編集 → ウィンドウを閉じる → ダイアログが出る。3つの選択肢それぞれで期待どおりに動く。

## Step 6: 最近開いたプロジェクト

**やること**
- 最近開いた(保存した)ファイルのパスを、最大10件、新しい順に保存する
- 起動時の画面またはメニューに一覧を出し、クリックで開く
- ファイルが存在しない項目は、一覧から外す(または灰色にして警告)

**説明**
- 保存場所は、OSのユーザー設定フォルダ(`dirs` クレートの `config_dir()` が便利)の下に `artoria/recent.json` のような形で置く。**プロジェクトファイルとは別にする**
- 設定フォルダの読み書きは `core` ではなく `app` 側に書く(OSやUIに依存するため)

**確認**: 3つのファイルを開いて一覧に出る。同じファイルを再度開いても重複せず、先頭に移動する。

## Step 7: DDLの `.sql` 書き出し

**やること**: 「DDLを書き出し」メニューで、`generate_ddl` の結果をファイルに保存する。

**説明**
- 区切りは、文のあとに空行を1つ入れる(Phase 1の方針どおり、`GO` は入れない)
- SSMS(SQL Server Management Studio)で開いて、そのまま実行できる形にしたい場合は、文の間に `GO` を入れるオプションを用意する。**デフォルトはなし**
- バリデーションエラーがあるときは、書き出しを無効にする(または警告して中止)
- 文字コードは **UTF-8(BOMなし)** にする。SSMSは、BOMなしのUTF-8を日本語の文字化けなしで開けない場合があるため、「BOM付きUTF-8」の選択肢を設定に用意しておくと安心

**確認**: 書き出した `.sql` を、実際にSSMSやAzure Data Studioで開いて、実行できる(DBに触れるのは、この確認だけ)。

## つまずきやすい点

- **日本語の識別子**: SQL Serverは `[顧客]` のような日本語の名前を扱える。`NVARCHAR` と `N'...'` の指定が必要なのは、DEFAULTに日本語の文字列リテラルを入れる場合(`N'未設定'`)。DEFAULT欄が生のSQL文字列なので、**ユーザーが `N` を付け忘れると文字化けする**。入力欄の下に注意書きを出すとよい
- **Windowsのファイルパス**: `\` と `/` の違いで悩むことはほぼない。Rustの `std::path::PathBuf` を使えば、OSに合わせて扱われる
- **保存後のdirty判定が残る**: 「最後に保存した `Schema`」の更新を、保存処理の**成功後に**行う。失敗時に更新すると、未保存なのに「保存済み」になる
