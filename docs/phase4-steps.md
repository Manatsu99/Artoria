## Step 0: テスト用のSQL Serverを用意する

**やること**: 次のどれかで、手元にSQL Serverを用意する。

- **Docker**(おすすめ。壊しても作り直せる)
- SQL Server Developer Edition(無償。開発・テスト用)
- SQL Server Express LocalDB(Windows)

Dockerの例:

```bash
docker run -e "ACCEPT_EULA=Y" -e "MSSQL_SA_PASSWORD=<強いパスワード>" \
  -p 1433:1433 --name artoria-sql -d mcr.microsoft.com/mssql/server:2022-latest
```

**説明**
- パスワードは、SQL Serverの複雑さの要件(大文字・小文字・数字・記号を含む8文字以上)を満たす必要がある。満たさないと、コンテナが起動してすぐ終了する
- 接続できるか確認するため、SSMSまたはAzure Data Studioで `localhost,1433`、ユーザー `sa` で繋いでみる
- テスト用に、空のデータベース(例: `ArtoriaTest`)を作っておく。`sa` で本番相当の操作をするのは避け、後でテスト専用ユーザーを作ってもよい

**確認**: SSMSなど既存のツールから、`SELECT @@VERSION` が実行できる。

## Step 1: `artoria-db` クレートの作成と接続の疎通

**やること**

```bash
cargo new --lib crates/artoria-db
```

- ルートの `members` に足す
- 依存を追加する(`artoria-core` も)

```toml
tiberius = { version = "0.12", features = ["rustls"] }   # 機能名は要確認(下記)
tokio = { version = "1", features = ["rt-multi-thread", "net", "macros"] }
tokio-util = { version = "0.7", features = ["compat"] }
artoria-core = { path = "../artoria-core" }
thiserror = "2"
```

最小の接続コード(これは概念の例。`async` 関数と `#[tokio::main]` が必要):

```text
1. tiberius の Config を作る(ホスト、ポート、認証、DB名)
2. TCPで接続する(tokio::net::TcpStream)
3. そのストリームを .compat_write() で包み、Client::connect に渡す
4. client.simple_query("SELECT @@VERSION") を実行し、結果を読む
```

**説明**
- **tiberiusの機能(feature)の名前は、バージョンで異なる。** 依存を足す前に、`tiberius` のドキュメント(docs.rs)の「Feature flags」を確認する。TLSの実装(`rustls` / `native-tls`)と、Windows認証用の機能(`winauth` や `integrated-auth-gssapi`)の指定がここに関わる
- tiberiusは **tokioのストリーム** ではなく **futuresのストリーム** を要求する。そのため `tokio_util::compat` で包む(`.compat_write()`)
- ローカルの開発用SQL Serverは自己署名証明書を使うため、`config.trust_cert()` が必要になる(**開発用の設定。本番では証明書の検証を有効にする**)
- `simple_query` の戻り値(`QueryStream`)は、**最後まで読み切る**必要がある(`.into_results().await?` など)。読まずに捨てると、次のクエリが失敗する

**確認**: `cargo run` の小さなサンプル(`examples/connect.rs` など)で、`SELECT @@VERSION` の結果が表示される。

## Step 2: 接続設定のモデルと接続テスト

**やること**: `artoria-db` に、接続情報の構造体と、接続テスト関数を作る。

```text
ConnectionSettings {
    host, port, database,
    auth: Auth,            // SqlServer { user, password } / Windows
    trust_server_certificate: bool,
    environment_label: Environment   // 開発 / テスト / 本番 (Step 9で使う)
}
```

```text
test_connection(&ConnectionSettings) -> Result<ServerInfo, DbError>
```

`ServerInfo` はサーバーのバージョンとDB名。

**説明**
- 認証は2種類。
  - **SQL Server認証**: ユーザー名とパスワード
  - **Windows認証**: ログイン中のWindowsユーザーで繋ぐ。Windowsでは `winauth` 機能で対応できる。他のOSでは追加の設定が必要になるので、まずSQL Server認証だけで進めてもよい
- パスワードの型は `String` ではなく、**構造体のフィールドとして持つが、`Debug` 出力には出さない**ようにする(ログやエラー表示にパスワードが出てしまうのを防ぐ)。`Debug` を手書きで実装して、パスワードを `***` にするのが簡単
- `ConnectionSettings` を `Serialize` するとき、**パスワードは含めない**(Step 6で別の場所に保存する)

**確認**: 正しい設定で成功し、パスワードを間違えると「認証エラー」と分かるエラーが返る。ポートを間違えると「接続できない」と分かるエラーが返る。

## Step 3: DDLのトランザクション実行

**やること**: 次の関数を書く。

```text
execute_ddl(&ConnectionSettings, statements: &[String]) -> Result<ExecutionReport, DbError>
```

**実行の流れ**

1. 接続する
2. `SET XACT_ABORT ON;` を実行する
3. `BEGIN TRANSACTION;` を実行する
4. 文を1つずつ実行する
5. 全部成功したら `COMMIT;`
6. 途中で失敗したら `ROLLBACK;` して、どの文で失敗したかを返す

**説明**
- SQL Serverは、`CREATE TABLE` や `ALTER TABLE`、`CREATE INDEX` といったDDLを**トランザクションに入れられる**。途中で失敗しても、`ROLLBACK` で何も作られなかった状態に戻せる。これがこのツールの大きな価値になる
- `SET XACT_ABORT ON` を付ける理由は、エラーが起きたときにSQL Server側でトランザクションが自動的に中止されるようにするため。付けないと、エラー後もトランザクションが開いたままになることがある
- 例外: `CREATE DATABASE` や一部のDDLはトランザクションに入れられない。Phase 4では `CREATE TABLE` / `ALTER TABLE` / `CREATE INDEX` だけを扱うので問題ない
- `GO` は送らない(Phase 1の方針どおり)
- 文は **1つずつ `simple_query`** で送る。各戻り値を最後まで読み切る
- **文の実行前に、失敗したら必ず `ROLLBACK` する** 処理を書く。`ROLLBACK` 自体が失敗した場合(接続が切れていた場合など)も、エラーとして返す

**確認(Dockerの練習用DBに対する統合テスト)**
- Phase 1の `sample_schema()` のDDLを実行し、テーブルがすべてできている
- わざと2つ目の文を失敗させる(存在しないテーブルをFKで参照する)と、1つ目の `CREATE TABLE` も残らない
- 同じDDLを2回実行すると、2回目は「すでに存在する」エラーになり、`ROLLBACK` される

統合テストは、Dockerが起動していないときにスキップ(または `#[ignore]`)できるようにしておくと、普段の `cargo test` が止まらない。

## Step 4: エラーに文脈を付ける

**やること**: `DbError` を整理する。

- どの文(何番目、どの文の先頭)で失敗したか
- SQL Serverのエラー番号とメッセージ(tiberiusのエラーから取り出せる)
- 接続系のエラー(接続できない、認証失敗、タイムアウト)と、実行系のエラー(SQLのエラー)を区別する

**説明**
- 画面に出すメッセージは、「テーブル `dbo.Orders` の外部キー `FK_Orders_Users` の作成に失敗: ...」のように、**ユーザーが原因を推測できる情報**を含める
- よくあるエラー番号に、親切なメッセージを付ける。例:
  - `2714`: すでに同名のオブジェクトがある
  - `1767`: FKの参照先が見つからない
  - `1750`: 制約の作成に失敗
  - `229`: 権限がない
  - 番号は追加で調べ、**調べた番号だけ**対応する(全部は不要)
- どの文で失敗したかを特定するため、`ExecutionReport` に「成功した文の数」「失敗した文のインデックス」を持たせる

**確認**: Step 3の失敗ケースで、失敗した文とSQL Serverのメッセージが `DbError` から取り出せる。

## Step 5: tokio と GPUI の橋渡し

**やること**: 画面から `artoria-db` の `async` 関数を呼べるようにする。

**説明**
- tiberiusは **tokio** の上で動く。GPUIは **独自のexecutor** を持つ。この2つは、そのまま混ぜられない
- 方針: **アプリ起動時に tokio のランタイムを1つ作って持っておく**。DB処理はそのランタイムで実行し、完了したら結果をチャネルで GPUI 側に返す
  1. アプリ全体で使う `tokio::runtime::Runtime` を作る(`artoria-app` の状態に持つ)
  2. 画面のボタンから、`runtime.spawn(async { ... })` でDB処理を投げる
  3. 結果を受け取るチャネル(`async-channel` など)を作り、GPUI側の `cx.spawn` で結果を待つ
  4. 結果を受け取ったら、画面の状態を更新して `cx.notify()` を呼ぶ
- **画面のスレッドでDB処理を待たない。** 待つと、接続中にウィンドウが固まる
- `gpui` の関連クレートに、tokioとの連携を助けるものがあるかもしれない。調べて、あればそれに従う

**確認**: 画面のボタンを押すと、画面を固めずにDBへ接続して結果(`SELECT @@VERSION`)が表示される。

## Step 6: 接続設定画面と資格情報の保存

**やること**
- 接続設定の入力フォーム(ホスト、ポート、DB名、認証方式、ユーザー、パスワード、証明書を信頼するか、環境ラベル)
- 「接続テスト」ボタン(結果を画面に表示)
- 接続設定の保存・一覧・削除
- パスワードの保存

**説明**
- 接続設定(パスワード以外)は、Phase 3の「最近開いたプロジェクト」と同じく、OSの設定フォルダ(`dirs` クレート)にJSONで保存する
- **パスワードは、そのJSONに平文で保存しない。** OSの資格情報ストア(Windowsの資格情報マネージャー、macOSのキーチェーンなど)に入れる。Rustでは `keyring` クレートで扱える
- パスワードを保存しない選択肢も用意する(接続のたびに入力する)
- **プロジェクトファイル(`.artoria`)に接続情報を含めない。** ファイルを共有したとき、サーバー名やDB名が漏れるのを防ぐ。プロジェクトと接続先は、別の概念として扱う

**確認**: 接続設定を保存し、アプリを再起動しても一覧に残る。パスワードを保存した設定で、入力なしに接続テストが通る。設定ファイルの中身を開いて、パスワードが含まれていないことを確認する。

## Step 7: 実行の確認ダイアログと結果表示

**やること**
- 「データベースに適用」ボタンを付ける
- 押すと、確認ダイアログを出す。内容:
  - 接続先(サーバー、DB名、環境ラベル)
  - 実行するSQLの全文(スクロールできる)
  - 文の数
  - 「実行」「キャンセル」
- 実行中は、進捗(何番目の文か)を表示する。キャンセルや二重実行ができないようにボタンを無効にする
- 結果を表示する:
  - 成功: 作成したオブジェクトの数
  - 失敗: どの文で、何のエラーで失敗したか。`ROLLBACK` 済みであること

**説明**
- バリデーションエラーがあるときは、ボタンを無効にする
- 実行はStep 5のチャネルで、**文ごとに進捗を送る**(進捗の更新用と最終結果用)
- 実行中にウィンドウを閉じようとしたら、警告する

**確認**: 練習用DBに対して、画面から実行して成功する。わざと失敗する設計(存在しないカラムをFKで参照など。バリデーションを通る範囲で)で、失敗して何も残らない。

## Step 8: 実行ログの保存

**やること**
- 実行のたびに、次をログファイルに残す
  - 日時
  - 接続先(サーバー、DB名。**パスワードは含めない**)
  - 実行したSQL
  - 結果(成功・失敗、エラー内容)
- 「ログを開く」メニューで、ログの場所を開く、または画面で一覧表示する

**説明**
- ログの置き場所は、OSの設定フォルダの下の `artoria/logs/`。日付ごとにファイルを分けると管理しやすい
- 後で「いつ・どのDBに・何を実行したか」を確認できるのは、DBを触るツールでは重要な機能
- ログが増え続けるのを避けるため、古いログの削除(例: 90日より前)は、後回しでよい

**確認**: 実行後にログファイルができて、成功・失敗の両方が記録されている。

## Step 9: 安全策(本番ラベル・衝突の事前チェック)

**やること**

**環境ラベル**
- 接続設定に、「開発」「テスト」「本番」のラベルを付けられるようにする
- 本番のときは、確認ダイアログに目立つ警告を出し、**追加の確認**(DB名の再入力など)を求める
- 接続中の環境が一目で分かるように、画面の上部に色付きの帯を出す

**既存オブジェクトとの衝突チェック**
- 実行前に、DB上に同名のテーブルがすでにあるかを問い合わせる(`sys.tables` と `sys.schemas`)
- あれば、「すでに存在します。実行すると失敗します」と警告する(失敗はロールバックされるが、事前に分かるほうが親切)

**説明**
- 衝突チェックは、後のPhase 5(既存DBの読み取り)の仕組みの一部を、先取りした形になる。まず、テーブル名の存在確認だけでよい
- 「本番」ラベルは、**ユーザーが自分でつけるもの**。ツール側で本番かどうかを判定することはできない

**確認**: 「本番」ラベルの接続で、実行前に追加の確認が出る。既存テーブルと同名のテーブルを含む設計で、事前に警告が出る。

## つまずきやすい点

- **接続できない**: SQL Serverの設定で、TCP/IP接続が無効になっていることがある(Dockerなら通常は有効)。ファイアウォール、ポート番号、インスタンス名(`localhost\SQLEXPRESS` のような名前付きインスタンスは、ポートが動的になる)を確認する
- **証明書のエラー**: 開発用の自己署名証明書は、`trust_cert()` を付けないと拒否される
- **`QueryStream` を読み切らない**: 次の文で「前のクエリが完了していない」というエラーになる
- **`ROLLBACK` し忘れ**: エラー経路で、必ず `ROLLBACK` を通るように、`match` や `?` の使い方を見直す。エラーが起きる位置を問わず後始末ができる構造にする
- **tiberiusのバージョンと機能名**: 記事やサンプルが古いと、機能名やAPIが一致しない。使っているバージョンのドキュメントを優先する
