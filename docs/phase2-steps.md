## Step 0: `artoria-app` クレートの作成とGPUI起動確認

**やること**

```bash
cargo new crates/artoria-app
```

- ルートの `Cargo.toml` の `members` に `crates/artoria-app` を足す
- `artoria-app/Cargo.toml` に `gpui` と `artoria-core`(パス指定)を足す
- `gpui` は **バージョンを固定する**(`=` 指定)
- 空のウィンドウが開く `main.rs` を書く(最小のウィンドウは、最初にやりとりしたコードを参照)

```toml
artoria-core = { path = "../artoria-core" }
```

**説明**

- `gpui-component`(ボタン、テキスト入力、テーブルなどの部品集)を使うかどうかを、**ここで決める**。自作すると、テキスト入力やドロップダウンだけで大きな作業になる。使うなら、READMEの初期化手順に従い、`gpui` とバージョンが合うものを選ぶ
- GPUIはZed(エディタ)から切り出されたフレームワークで、ドキュメントが薄い。**動くサンプルを読むのが一番早い**(`gpui` リポジトリの `examples`、`gpui-component` のサンプル集)
- ビルドに時間がかかる。最初の1回は特に長い

**確認**: `cargo run -p artoria-app` で空のウィンドウが開き、閉じられる。

## Step 1: core: スキーマの編集操作

**やること**: `artoria-core/src/edit.rs` を作り、`Schema` に編集用のメソッドを足す。

| 操作 | 内容 |
|---|---|
| テーブル | 追加、削除、名前変更、複製 |
| カラム | 追加、削除、名前変更、並べ替え(上下に移動)、型などの変更 |
| 主キー | カラムの追加・削除・順序変更 |
| 外部キー | 追加、削除、変更 |
| インデックス | 追加、削除、変更 |

**説明: 「波及」を忘れない**

名前の変更や削除は、他の場所に影響する。ここがロジックの核心になる。

- カラム名を変えたら、**主キー・インデックス・外部キーの中の同じカラム名も一緒に書き換える**
- テーブル名を変えたら、**他のテーブルの外部キーの `ref_table` も書き換える**
- カラムを削除したら、そのカラムを使っているPK・インデックス・FKをどうするか決める(**一緒に消す**のが分かりやすい。消した内容を呼び出し側に返すと、画面で「〇〇も削除された」と知らせられる)
- テーブルを削除したら、そのテーブルを参照している外部キーも消す

**判断メモ**
- 各操作は `Result<(), EditError>` を返す(存在しないテーブル名を指定した場合など)
- 新規追加時の名前は自動採番(`NewTable1`, `NewTable2` ...)。画面の「追加」ボタンですぐ使える
- 名前変更は、**この編集操作経由でのみ行う**。画面でフィールドを直接書き換えると、波及が漏れる。Phase 6で既存DBを編集するときにも効く

**確認(テストで)**
- カラム名変更で、PK・インデックス・FKが追従する
- テーブル名変更で、他テーブルのFKの参照先が追従する
- カラム削除で、そのカラムを使うインデックスが消える
- 存在しない名前を指定するとエラーになる
- 操作後に `validate` を通すと、エラーが出ない

## Step 2: core: Undo / Redo の履歴

**やること**: `artoria-core/src/history.rs` を作る。

```text
History { undo: Vec<Schema>, redo: Vec<Schema> }
```

**説明**

- 方式は **スナップショット方式**。編集の前の `Schema` を丸ごと `Clone` して積む。Phase 1で `Clone` と `PartialEq` を付けたので、そのまま使える
- テーブル数が数百規模でも、メモリは問題にならない
- 操作ごとに「逆操作」を実装する方式は、バグの元になる。スナップショットのほうが確実

**必要な動作**

- `push(&mut self, before: Schema)`: 編集前の状態を積む。**redoは空にする**(新しい編集をしたらやり直し履歴は無効)
- `undo(&mut self, current: Schema) -> Option<Schema>`
- `redo(&mut self, current: Schema) -> Option<Schema>`
- 履歴の上限(例: 100件)を超えたら古いものから捨てる

**判断メモ**: 連続した文字入力(名前を1文字ずつ打つ)を1回の編集にまとめるかどうかは、画面ができてから決める。最初は「確定したとき1回」で十分。

**確認(テストで)**: 編集 → undo → redo で、元の状態と `==` になる。undo後に新しい編集をすると redo できなくなる。

## Step 3: app: 状態の持ち方と3ペインの骨組み

**やること**: 画面の状態を2種類に分けて持つ。

| 種類 | 例 | 持ち方 |
|---|---|---|
| **ドキュメント状態** | `Schema`、`History` | 1か所(`Document`)にまとめる。保存・Undoの対象 |
| **画面状態** | 選択中のテーブル、選択中のカラム、スクロール位置 | 画面側。保存もUndoもしない |

**説明**

- GPUIでは、状態を持つ部品を `Entity<T>`(共有できる所有者付きの状態)で持ち、変更したら `cx.notify()` で「再描画して」と通知する。C#のWPFでいう `INotifyPropertyChanged` + `ViewModel` に近い
- `Document` を1つの `Entity` にして、3つのペイン(テーブル一覧・カラム編集・DDLプレビュー)がそれを観察する(`observe`)形にすると、**編集のたびにDDLプレビューが自動で更新される**
- **選択状態は `Schema` に入れない。** 入れると、選択を変えるだけでUndo履歴が増える

**レイアウト**
- 左: テーブル一覧
- 中央: カラム編集グリッド
- 右(または下): DDLプレビュー

**確認**: 3つの領域に仮のテキストが表示される。`Document` を変更すると、全ペインが再描画される(ボタン1つで `Schema` にテーブルを足して確認)。

## Step 4: テーブル一覧ペイン

**やること**
- テーブルを一覧表示する(`スキーマ名.テーブル名`)
- クリックで選択する
- 「追加」「削除」「複製」ボタンを付ける
- 名前の変更(ダブルクリックまたはボタンでテキスト入力に切り替え)

**説明**
- ボタンの処理は、Step 1の編集操作を呼ぶだけ。**呼ぶ前に `History::push` で現在の状態を積む**
- 削除は確認ダイアログを出す。波及して消えるもの(FKなど)がある場合は、その内容も表示する
- 削除後の選択状態に注意する(最後のテーブルを消したら選択なし、など)

**確認**: 追加 → 名前変更 → 複製 → 削除ができる。DDLプレビューが連動して変わる。

## Step 5: カラム編集グリッド

**やること**: 選択中のテーブルのカラムを、表(グリッド)で編集する。

| 列 | 入力方法 |
|---|---|
| 名前 | テキスト |
| 型 | ドロップダウン(`SqlType` の種類) |
| 長さ・精度 | 型に応じて入力欄を出し分ける(NVARCHAR→長さ、DECIMAL→精度と小数桁) |
| NULL可 | チェックボックス |
| IDENTITY | チェックボックス |
| DEFAULT | テキスト(空なら `None`) |
| 主キー | チェックボックス(Step 6で本格対応) |

さらに、行の追加・削除・上下移動のボタンを付ける。

**説明**
- 型を切り替えたとき、`SqlType` のケースを作り直す(例: `Int` → `NVarChar(Some(50))`)。新しい型の既定値を決めておく
- 「長さ」が空のとき `None`(= MAX)、数字が入っていれば `Some(n)` に変換する。数字以外が入力されたらエラー表示にする
- 入力途中の値(例: 空文字)を `Schema` に反映して構わないかを考える。**反映するならバリデーションエラーが出るだけ**で、不正な状態でも画面は壊れない設計にする
- この表がPhase 2で最も作業量が大きい。**最初は名前・型・NULL可の3列だけ作り、動いてから列を足す**

**確認**: カラムを追加し、各項目を編集でき、DDLプレビューにすべて反映される。

## Step 6: 主キー・外部キー・インデックスの編集

**やること**

**主キー**
- カラム編集グリッドの「主キー」チェックで、`primary_key` の追加・削除をする
- 複合キーの順序を変えるUI(上下移動)を付ける

**外部キー**
- テーブルの下に「外部キー」の一覧を出す
- 追加: 参照先テーブルをドロップダウンで選び、カラムのペア(参照元 → 参照先)を選ぶ
- 名前は自動で `FK_参照元_参照先` を入れる(変更も可能)

**インデックス**
- 一覧を出し、追加・削除・名前変更
- 対象カラムを選択(複数、順序あり)、UNIQUEのチェック

**説明**
- 外部キーの参照先カラムは、**参照先テーブルのカラムだけ**を選択肢に出す。絞り込めば、バリデーションエラーの多くが起きなくなる
- 参照先テーブルを変えたら、選択済みの参照先カラムをクリアする

**確認**: 2テーブルを作り、FKを張り、UNIQUEインデックスを付けると、Phase 1の `sample_schema()` と同じ内容のDDLがプレビューに出る。

## Step 7: DDLプレビューとエラー表示

**やること**
- 右(下)ペインに、`generate_ddl` の結果を表示する
- バリデーションエラーがあるときは、DDLの代わりに(または上に)エラー一覧を表示する
- エラーをクリックすると、該当のテーブル・カラムが選択される
- カラム編集グリッドの該当セルに、エラーの印(赤枠など)を付ける
- 「DDLをコピー」ボタンを付ける

**説明**
- `ValidationError` が「どのテーブル・どのカラムか」の情報を持っていれば、この対応づけができる。**情報が足りなければ、Phase 1の `ValidationError` に足す**(ここで気づくのが普通)
- 再生成が重い場合に備え、`Schema` が変わったときだけ再生成する。ただし、まず作ってみて重いと感じてから最適化する

**確認**: わざと壊した状態(同名のカラムなど)で、エラーが出て、クリックで場所に移動できる。

## Step 8: キーボード操作と Undo / Redo の接続

**やること**
- `Ctrl+Z` / `Ctrl+Y`(Macは `Cmd`)で、Step 2の履歴を使った Undo / Redo
- Undo後は `Document` の `Schema` を置き換え、選択状態が範囲外にならないように補正する
- 表の中で `Tab` で次のセル、`Enter` で確定、`Esc` で取り消し
- テーブル追加・カラム追加のショートカット

**説明**
- GPUIでは、操作を **アクション**(名前付きのコマンド)として定義し、キーバインドに割り当てる。C#のWPFの `RoutedCommand` と `KeyBinding` に近い
- Undoで `Schema` が変わると、選択中のテーブルが存在しなくなることがある。**選択は名前で持たず、インデックスで持っているなら範囲チェックを入れる**

**確認**: 一連の編集を、`Ctrl+Z` で順に戻し、`Ctrl+Y` でやり直せる。

## つまずきやすい点

- **GPUIのエラーメッセージが分かりにくい**: 借用(`&mut cx`)のエラーが多い。`Entity` の中身を更新するときは `update` 経由で、**更新中に同じ `Entity` を読もうとしない**
- **入力欄の途中状態**: 数字欄に `-` だけ入力された、のような途中の値を許容する(確定時にだけ検証する)
- **波及の漏れ**: 画面から `Schema` のフィールドを直接書き換えたくなったら、Step 1の編集操作に足す
- **全部を一度に作ろうとして止まる**: Step 5は3列だけ、Step 6はPKだけ、のように縮めて先へ進む
